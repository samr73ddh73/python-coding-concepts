- Why not B-Tree?

B-Tree can index lat and long separately.
So, if we need to find all the lats with x kms of a given lat, we can do that

but location is 2 dimension, we need to deal with both lat and lon separately.


and thus, B-tree will not be in efficient here. 


Thus, we move to hash based appraoch known as geohash. In geohash, we convert 2D coordinates into 1D string, which can easily be indexed and we can use B-tree to do proximity search on them then.

How it works, we divide the world into zones (quadrant), each zone is named something and then we keep dividing it and the name keeps getting updated

the length of the geohash tells us how small we are going. nearer location share same prefix (except the boundary ones)


Then we have QuadTree and then R-Tree


R-tree is what is used everywhere (pos-gis, postgres etc)


Learn this:
"Traditional indexes like B-trees don't work well for spatial data because they treat latitude and longitude as independent dimensions. To efficiently search for nearby locations, we need an index that understands spatial relationships. Geohash is a hash-based approach that converts 2D coordinates into a 1D string, preserving proximity. This allows us to use a regular B-tree index on the geohash strings for efficient proximity searches. However, tree-based approaches like R-trees can offer more flexibility and accuracy by grouping nearby objects into overlapping rectangles, creating a hierarchy of bounding boxes."
By contrasting these two approaches, you demonstrate a deeper understanding of the trade-offs involved in geospatial indexing."

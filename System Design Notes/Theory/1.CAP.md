## What is CAP Theorem?

In any distributed system, you can only **guarantee 2 out of 3** properties:

| Property | Meaning |
|---|---|
| **C — Consistency** | Every read returns the most recent write (linearizability) |
| **A — Availability** | Every request gets a response (no timeouts, no errors) |
| **P — Partition Tolerance** | System continues operating despite network partitions |

As established in your last question — **P is non-negotiable** in real distributed systems. So the real choice is always **CP vs AP**.

---

## CP vs AP — What you're actually choosing

### CP — Consistency over Availability
When a partition occurs, the system **refuses to respond** rather than return stale data.

- You'd rather return an error than wrong data
- Use when **correctness is critical**
- Examples: **Zookeeper, etcd, HBase, Redis (cluster mode)**

### AP — Availability over Consistency
When a partition occurs, the system **still responds** but data may be stale.

- You'd rather return something than nothing
- Use when **uptime and responsiveness matter more than perfect accuracy**
- Examples: **Cassandra, DynamoDB, CouchDB**

---

## How to apply this in a system design interview

The key skill interviewers are testing is: **can you justify your DB/storage choice based on the consistency requirements of each component?**

Most large systems are **not uniformly CP or AP** — different components have different requirements.

### Framework: Ask yourself per component —
```
"What happens if a user reads stale data here?"
        ↓
Catastrophic (money, auth, inventory)?  →  CP
        ↓
Tolerable (likes, views, feed)?  →  AP
```

---

## Applied examples by domain

### 1. Payments / Bank transfers
**CP strictly.** If two nodes disagree on a balance, you have a fraud problem. You'd rather the transaction fail than double-spend.
→ Use: PostgreSQL, CockroachDB, or distributed transactions with strong consistency.

### 2. Inventory / Flash sales (e.g. Amazon, Flipkart)
**CP for the final decrement.** You cannot oversell 1 item to 5 buyers.
→ Use: Redis with Lua scripts (atomic) or DB row-level locking for the critical decrement. AP for displaying stock count to browsers — showing "~10 left" with slight staleness is fine.

### 3. Social media feed / Likes / View counts
**AP.** If your like count shows 9,999 instead of 10,000 for 200ms, nobody cares.
→ Use: Cassandra, DynamoDB. Eventual consistency is perfectly acceptable.

### 4. User authentication / Sessions
**CP.** If a user logs out and a stale node still considers them logged in, that's a security issue.
→ Use: Redis (single primary) or a strongly consistent store for session tokens.

### 5. Distributed config / Leader election (e.g. which node is primary?)
**CP strictly.** Split-brain (two nodes both think they're leader) is catastrophic.
→ Use: Zookeeper, etcd. These are purpose-built CP systems.

### 6. Search indexes / Recommendations
**AP.** Slightly stale search results or recommendations are invisible to users.
→ Use: Elasticsearch (AP by default), eventual consistency is fine.

## The mature answer — PACELC

CAP only talks about behavior **during partitions**. But partitions are rare. **PACELC** covers the rest:

```
If Partition:     choose C or A  (CAP)
Else (normal):    choose L or C  (Latency vs Consistency)
```

Even without a partition, strong consistency requires coordination between nodes → **higher latency**. AP systems like Cassandra give you low latency because they don't wait for all nodes to agree.

**DynamoDB, Cassandra** = PA/EL — Available during partition, Low latency normally  
**Zookeeper, etcd** = PC/EC — Consistent during partition, Consistent normally (higher latency)

## 🎯 Interviewer-level talking points

- **Never say "I'll use Cassandra because it's fast."** Say: *"This component has eventual consistency tolerance, so I'll use Cassandra — it's AP, gives me high availability and low write latency, and the business can tolerate a few seconds of staleness here."*
- **Hybrid architectures** — use CP for writes (source of truth), AP for reads (cache/replica). Write to PostgreSQL, read from Redis. Classic pattern.
- **Quorum reads/writes** — Cassandra lets you dial consistency per operation. `QUORUM` (majority of nodes must agree) gives you tunable CP-like behavior without fully sacrificing availability. Mention this shows you understand it's a spectrum, not binary.
- **CAP C ≠ ACID C** — re-emphasize this if it comes up. Interviewers test this.
- **Two-phase commit (2PC)** — the classic protocol for achieving CP across distributed nodes. Know its failure modes: coordinator failure leaves participants blocked (why people moved to Paxos/Raft).
- **Raft / Paxos** — consensus algorithms that implement CP correctly. etcd uses Raft. Knowing this one level deeper signals senior-level thinking.

## One-line interview summary you can deliver

> *"CAP tells me that during a network partition I must choose between consistency and availability. Since partitions are inevitable, I design each component independently — CP where data correctness is non-negotiable, AP where availability and latency matter more and staleness is tolerable. In normal operation, PACELC reminds me there's also a latency-consistency tradeoff even without partitions."*
